What is Readiness Probe?
=============================

Readiness Probe checks whether the application is ready to accept user requests. If the check fails, Kubernetes stops sending traffic to the pod but does not restart it.

readinessProbe:
  httpGet:
    path: /health
    port: 8080


Kubernetes checks http://<pod-ip>:8080/health to see if the application is ready to receive user traffic.


If /health returns 200 OK --> send traffic to ap
If /health fails --> Kubernetes does NOT restart the Pod.







=========================
What is Liveness Probe?
=========================

Liveness Probe checks whether the application is healthy and running. If the check fails, Kubernetes restarts the container automatically.



It will check the application is live for evry time below syntax:


livenessProbe:
  httpGet:
    path: /health
    port: 8080



Means :

http://localhost:8080/health //curl http://<pod-ip>:8080/health


and the application returns:

{
  "status": "UP"
}


✅ Application is healthy

✅ No action needed



If we got failure it reastart the application 



Liveness Probe Failed
↓
Kubernetes Restarts Container




✅ Readiness = Stop Traffic
 ✅ Liveness = Restart Container

Ingress
=======

Problem with LoadBalancer :

A LoadBalancer exposes one service to the outside world.

Suppose you have 3 applications:

Employee App
Product App
Order App

Using LoadBalancer:


Employee App → LoadBalancer1 → Public IP1
Product App  → LoadBalancer2 → Public IP2
Order App    → LoadBalancer3 → Public IP3


❌ Multiple Public IPs

❌ Higher cloud cost



Feature	   	LoadBalancer	     	Ingress
Exposes Service	   Yes			Yes
Multiple Apps       No		        Yes
URL-based Routing   No	                Yes
Host-based Routing  No	                 Yes
Cost	         Higher	                   Lower
Public IPs	One per Service 	One for many Services







Ingress is a Kubernetes resource that routes external traffic to services based on:

Host name
URL path


Internet
    |
Ingress
    |
-----------------------
|          |          |
Emp      Product    Order
Svc       Svc        Svc

Instead of :

52.10.10.1
52.10.10.2
52.10.10.3

Users access:


company.com/employee
company.com/product
company.com/order


In Pod runs the application, 
Service exposes the Pods, and 
Ingress exposes multiple Services using a single domain name and 
routes traffic to the correct application.

Rolling update:
===============


Rolling Update means updating an application gradually without downtime.

Instead of stopping all old pods and creating new ones, Kubernetes replaces pods one by one (or in batches) so users can continue accessing the application.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deploy
spec:
  replicas: 3

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1

  selector:
    matchLabels:
      app: nginx

  template:
    metadata:
      labels:
        app: nginx

    spec:
      containers:
      - name: nginx
        image: nginx:1.24
        ports:
        - containerPort: 80


now update to v2
=============
kubectl set image deployment/nginx-deploy nginx=nginx:1.25

Check new vesion :


kubectl rollout status deployment/nginx-deploy

now v2 has some issues rollback the previous version :
==============================================
kubectl rollout undo deployment/nginx-deploy


ReplicaSet is used to maintain the desired number of Pods and provides self-healing and scaling. Deployment is a higher-level Kubernetes object that manages ReplicaSets and provides advanced features like rolling updates, rollback, and revision history. In real-time projects, we generally use Deployments instead of directly creating ReplicaSets.


ReplicaSet = Pod Manager


Deployment = ReplicaSet Manager
             + Rolling Update
             + Rollback
             + Version History

Startegy:
===========

1. Recreate ----> existing pods willl be deleted and new pods will be created.

2. Rolling Update ---> Instead of stopping all old pods and creating new ones, Kubernetes replaces pods one by one (or in batches) so users can continue accessing the application.


ReplicaSet = Keep Pods Alive

Deployment = Keep Pods Alive + Rolling Update + Rollback

Blue Green-Deployment
==========================
Blue-Green Deployment is a deployment strategy to release a new version with zero/minimum downtime.

Blue  = Current Version (v1) ✅
Green = New Version (v2) ✅


Advantages 

✅ Rapid Releasing: Deploy new version quickly.

✅ Simple Rollbacks

If Green fails:

Green ❌
Switch back to Blue ✅



"In Kubernetes Blue-Green deployment is usually implemented by running two deployments with different labels (blue/green) and changing the Service selector to switch traffic between them.


maxUnavailable → How many pods can go DOWN?

maxSurge → How many EXTRA pods can be created?

Auto-Scaling :(HPA)-->based on metrics pods will be increased /decreased
===============
✅ 200m CPU = 0.2 CPU core
 ✅ 500m CPU = 0.5 CPU core
 ✅ 256Mi = guaranteed memory
 ✅ 512Mi = maximum memory allowed


Requests = minimum guaranteed resources used by scheduler for pod placement.

Limits = maximum resources a container is allowed to consume.

CPU exceeds limit → throttled
Memory exceeds limit → OOMKilled


Step 1: Deployment


apiVersion: apps/v1
kind: Deployment
metadata:
  name: springboot-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: springboot-app
  template:
    metadata:
      labels:
        app: springboot-app
    spec:
      containers:
      - name: springboot-app
        image: myrepo/springboot-app:v1
        ports:
        - containerPort: 8080

        resources:
          requests:
            cpu: "200m"
            memory: "256Mi"

          limits:
            cpu: "500m"
            memory: "512Mi"





CPU Request = 200m
Current Usage = 140m

Utilization = 140/200 × 100
            = 70%







apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: springboot-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: springboot-app

  minReplicas: 2
  maxReplicas: 10

  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

Daemons set
==========
DaemonSet is a Kubernetes controller that ensures one Pod runs on every worker node.

===================
1. Log Collection (Most Common)
===============================
Companies use Fluentd, Fluent Bit, Filebeat as DaemonSets.

✅ Why?

Every node generates logs.
One log collector pod runs on each node.
Collects logs and sends them to ELK (Elasticsearch, Logstash, Kibana) or Splunk.

Node1 -> Fluent Bit Pod
Node2 -> Fluent Bit Pod
Node3 -> Fluent Bit Pod


=================
2. Monitoring Agents
========================

Tools:

Prometheus Node Exporter
Datadog Agent
New Relic Agent

✅ Why?

Need CPU, Memory, Disk metrics from every node.
DaemonSet ensures monitoring agent exists on all nodes.


DaemonSet is used when a pod must run on every node, such as log collectors, monitoring agents, security agents, network plugins, and storage drivers

apiVersion: apps/v1

  name: nginx-daemonset

spec:

    matchLabels:
      app: nginx

  template:
    metadata:
      labels:
        app: nginx
