Types of Node Affinity
==================================

1. requiredDuringSchedulingIgnoredDuringExecution  ---: Must match the condition. Otherwise, Pod won't be scheduled.

Required = Mandatory.

Preferred = Optional preference.

Mandatory	                 Optional

Hard scheduling rule	               Soft scheduling rule

Kubernetes provides two settings:

Requests = Minimum requirement
How much CPU and memory the container asks Kubernetes to reserve for scheduling.

Limits = Maximum allowed
How much CPU and memory the container is allowed to consume.

resources:
  requests:
    cpu: "1"
    memory: "1Gi"
  limits:
    cpu: "2"
    memory: "2Gi"

Meaning:
- Request 1 CPU → Kubernetes uses 1 CPU as the scheduling requirement.
- Limit 2 CPU → Container can use up to 2 CPUs.
- Request 1 GB RAM.
- Limit 2 GB RAM.
So the container can use more than its request, but cannot exceed its limit.

==========================
Request = How much I need.
Limit = Maximum I can use.
*************************************************************

========================================================================================
CPU

When a container exceeds its CPU limit, Kubernetes throttles CPU usage.

It doesn't normally kill the container just because it exceeded the CPU limit.

Memory

When a container exceeds its memory limit, it can be killed by the Linux OOM mechanism.

You may see OOMKilled as the container termination reason

========================================================================================================
Scenario	Request	Limit	Meaning
1	No	No	No specified minimum or maximum
2	No	Yes	Request defaults to limit
3	Yes	Yes	Minimum scheduling requirement + maximum cap
4	Yes	No	Minimum scheduling requirement, can burst

1. What is LimitRange?
==========================
LimitRange is a Kubernetes object used to set minimum and maximum CPU and memory limits for containers or Pods within a namespace(********).



apiVersion: v1
kind: LimitRange
metadata:
  name: resource-limits
  namespace: dev
spec:
  limits:
    - type: Container
      min:
        cpu: "100m"
        memory: "128Mi"
      max:
        cpu: "2"
        memory: "2Gi"
      defaultRequest:
        cpu: "500m"
        memory: "512Mi"
      default:
        cpu: "1"
        memory: "1Gi"


defaultRequest = If a developer doesn't specify a resource request, Kubernetes automatically assigns this value as the request.

default = If a developer doesn't specify a resource limit, Kubernetes automatically assigns this value as the limit.

Imagine a company rule for developers:
- Minimum CPU allowed = 100m
- Maximum CPU allowed = 2
- If request is missing = Give 500m
- If limit is missing = Give 1 CPU
This is exactly what your LimitRange does!

5. What is Preemption?
This is a very important concept.
==========================

If a higher-priority Pod cannot be scheduled because lower-priority Pods are occupying resources,
 the scheduler may remove those lower-priority Pods to make room.

preemptionPolicy: PreemptLowerPriority

There are two options:
Value	Meaning
PreemptLowerPriority	The Pod can preempt lower-priority Pods if necessary.
Never	The Pod cannot preempt lower-priority Pods.

By default, the policy is PreemptLowerPriority.

Suppose:
- Node has 2 GB memory.
- Low-priority Pod uses 1.5 GB.
- High-priority Pod needs 1 GB.
- There isn't enough available memory.
What happens?

Kubernetes scheduler may remove (evict) a lower-priority Pod to make room for the higher-priority Pod.

This process is called Preemption.



Priority can be defined as high as 1 billion and as low as -2 billion or that number.

Larger Number--High Priority

kubectl get priorityClass.

  name: high-priority
value: 100000
globalDefault: false
description: "High priority for important applications"

Kubernetes normally has one default scheduler. 
We can run additional schedulers when we need different scheduling logic. A Pod selects which scheduler should handle it using schedulerName.

1. Why do we need Multiple Schedulers?
=====================================


Kubernetes has a default scheduler called:

default-scheduler

Its job is to select a suitable worker node for a Pod.


For example, when you create:

apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - name: nginx
    image: nginx


You didn't specify schedulerName.

So Kubernetes assigns the Pod to the default scheduler.

But sometimes we need special scheduling logic.

Application			Special scheduling requirement
AI/ML application		Schedule only on GPU nodes
High-performance application	Prefer nodes with specific hardware
Database application		Use custom placement/scoring logic
Batch workload			Use specialized scheduling policy

You can often handle these requirements with the default scheduler's existing features,
 
such as node affinity, taints, tolerations, and scheduling plugins. 

A separate scheduler is useful when you need genuinely different scheduling behavior.

2. How does a Pod select its scheduler?

This is the most important part of your guide.


apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  schedulerName: my-scheduler
  containers:
  - name: nginx
    image: nginx


schedulerName: my-scheduler

This Pod should be handled by a scheduler configured with the name my-scheduler.

The custom scheduler must actually be running and configured to handle that name.

If the scheduler is missing or configured with a different name, the Pod can remain Pending.

2. How does the scheduler select a Node?

==========================

1. Scheduling Queue

Pods wait for scheduling. Higher-priority Pods are generally processed first.


2. Filtering

Removes nodes that cannot run the Pod.

Example: Node doesn't have enough CPU.


3. Scoring

Gives scores to the remaining suitable nodes.

Example: Node A = 80, Node B = 60.


4. Binding

The scheduler assigns the Pod to the selected node.



Quick revision
- Scheduler → decides which Node runs a Pod.
- Profile → a set of scheduler settings and plugins.
- Plugin → performs a scheduling task.
- Extension point → stage where a plugin runs.
- Filtering → removes unsuitable Nodes.
- Scoring → ranks suitable Nodes.
- Binding → assigns Pod to Node.
- Multi-profile → multiple logical schedulers inside one scheduler process.
- schedulerName → Pod selects its scheduler profile.

Admission Controller
==========================
An Admission Controller is a component of the Kubernetes API server that checks or modifies a request before Kubernetes saves the object in etcd.

It can:
- Allow a request
- Reject a request
- Modify a request before saving it


Suppose a developer creates a Pod:

kubectl run nginx --image=nginx


Your company has a security policy:
All containers must use images from our company registry.

An admission controller can check the image:
- Company registry image → Allow
- Unapproved registry image → Reject
This helps enforce security policies across the cluster.

2. Where do Admission Controllers work?
Remember this flow:

1. kubectl

Developer sends a request to Kubernetes.


2. Authentication
Who are you?


3. Authorization (RBAC)

Are you allowed to perform this action?


4. Admission Controllers

Is this object allowed by cluster policy? Should it be modified?


5. etcd

If the request is accepted, the object is stored.

Interview point: Admission controllers run inside the API server's request processing path, after authentication and authorization, and before persistence.


A developer has permission to create Pods.
- RBAC says: "This developer can create Pods."
- Admission controller says: "But this Pod cannot run as root."

So, RBAC permission does not guarantee that the Pod will be accepted.


4. Two types of Admission Controllers:


Validating

Checks the request.

Accept or reject.

Example: Reject a Pod using a prohibited image.


Mutating

Modifies the request.

Example: Add default values or inject a sidecar container.

- Validating = Check it.
- Mutating = Change it.
Some admission plugins can perform both types of behavior


5. Important built-in Admission Controllers
Controller	Simple meaning
NamespaceLifecycle	Prevents creating resources in namespaces that don't exist and protects certain system namespaces
LimitRanger	Enforces resource limits and defaults defined by LimitRange
ResourceQuota	Enforces namespace resource quotas
PodSecurity	Enforces Pod security standards
NodeRestriction	Restricts kubelet requests related to Node and Pod objects
DefaultStorageClass	Assigns the default StorageClass to a PVC when appropriate

Note: Your lesson mentions NamespaceExists and NamespaceAutoProvision. These are older controllers. In modern Kubernetes, NamespaceLifecycle handles the main namespace lifecycle behavior.
6. Real-time example: ResourceQuota
Suppose your namespace has this quota:



apiVersion: v1
kind: ResourceQuota
metadata:
  name: my-quota
  namespace: dev
spec:
  hard:
    pods: "5"

he namespace allows a maximum of 5 Pods under this quota.

If a developer tries to create the 6th Pod, the API request can be rejected by the ResourceQuota admission controller.

This is how Kubernetes enforces namespace-level resource policies.



















: What are Admission Controllers in Kubernetes?

"Admission controllers are plugins in the Kubernetes API server request processing flow. They run after authentication and authorization but before the object is persisted to etcd. They can validate requests, reject requests, or mutate objects. For example, we can enforce security policies, restrict container images, apply defaults, and enforce resource quotas."
Quick revision
- Admission controllers run in the API server.
- They run after authentication and authorization.
- They run before persistence to etcd.
- Validating controllers check and accept/reject.
- Mutating controllers modify requests.
- RBAC controls user permissions; admission controllers enforce object policies.
One-line memory trick: RBAC checks the user; Admission Controller checks the request/object.
