Rolling Update :
===============

Rolling Update means updating an application gradually without downtime.

Instead of stopping all old pods and creating new ones, Kubernetes replaces pods one by one (or in batches) so users can continue accessing the application.


apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deploy
spec:
  replicas: 3

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1

  selector:
    matchLabels:
      app: nginx

  template:
    metadata:
      labels:
        app: nginx

    spec:
      containers:
      - name: nginx
        image: nginx:1.24
        ports:
        - containerPort: 80


kubectl apply -f deployment.yaml


Then we want update new version for all pods 


kubectl set image deployment/nginc-deploy nginx=nginx:.25

==========================

check history :

=====================
Overview of Deployment
=========================
Deployment in Kubernetes is an object that manages your Pods and ReplicaSets.

It helps you:

✅ Create Pods
✅ Scale Pods up/down
✅ Perform Rolling Updates
✅ Rollback to previous version
✅ Self-heal failed Pods

Suppose you have a Java application and want 3 copies (Pods) running all the time.

Instead of creating Pods manually, you create a Deployment.


apiVersion: apps/v1
kind: Deployment
metadata:
  name: java-app
spec:
  replicas: 3
  strategy:
    type: Recreate
  selector:
    matchLabels:
      app: java-app
  template:
    metadata:
      labels:
        app: java-app
    spec:
      containers:
      - name: java-app
        image: my-java-app:v1
``

What Happens?
Deployment creates a ReplicaSet.
ReplicaSet creates 3 Pods.
If a Pod crashes, ReplicaSet creates a new one.
If you update the image version, Deployment performs a r


kubectl apply -f deployment.yaml

kubectl get deployments

kubectl get pods

kubectl scale deployment java-app --replicas=5

kubectl set image deployment/java-app java-app=my-java-app:v2

kubectl rollout status deployment/java-app

kubectl rollout undo deployment/java-app


They are 2 stratergies in Deployment :


1. Recreate ----> existing pods willl be deleted and new pods will be created.

2. Rolling Update ---> Instead of stopping all old pods and creating new ones, Kubernetes replaces pods one by one (or in batches) so users can continue accessing the application.

===================
Blue -Green Deployment 
======================
Blue-Green Deployment is a deployment strategy to release a new version with zero/minimum downtime.

Blue  = Current Version (v1) ✅
Green = New Version (v2) ✅


Advantages 

✅ Rapid Releasing: Deploy new version quickly.

✅ Simple Rollbacks

If Green fails:

Green ❌
Switch back to Blue ✅

Rollback takes seconds.

✅ Built-in Disaster Recovery: Blue environment is always available as backup

✅ Seamless Customer Experience: Users don't notice deployment activity.

✅ Zero Downtime

Both environments run simultaneously.
No service interruption.


Example :

suppose :

Blue  = myapp:v1
Green = myapp:v2

Users use v1.--->Deploy v2 to Green.---->Test Green.---->Switch Service/Load Balancer to Green.

If issue occurs:

Green ❌
Switch back to Blue ✅

2 Pods
      ↓

HPA detects high CPU and automatically creates more pods.

2 Pods → 4 Pods → 6 Pods


========
When traffic drops:

6 Pods → 3 Pods → 2 Pods


This saves cost and prevents application crashes.

Step 1: Deployment


apiVersion: apps/v1
kind: Deployment
metadata:
  name: springboot-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: springboot-app
  template:
    metadata:
      labels:
        app: springboot-app
    spec:
      containers:
      - name: springboot-app
        image: myrepo/springboot-app:v1
        ports:
        - containerPort: 8080

        resources:
          requests:
            cpu: "200m"
            memory: "256Mi"

          limits:
            cpu: "500m"
            memory: "512Mi"

Step 2: Create HPA

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: springboot-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: springboot-app

  minReplicas: 2
  maxReplicas: 10

  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

===================
Blue -Green Deployment 
======================
Blue-Green Deployment is a deployment strategy to release a new version with zero/minimum downtime.

Blue  = Current Version (v1) ✅
Green = New Version (v2) ✅


Advantages 

✅ Rapid Releasing: Deploy new version quickly.

✅ Simple Rollbacks

If Green fails:

Green ❌
Switch back to Blue ✅

Rollback takes seconds.

✅ Built-in Disaster Recovery: Blue environment is always available as backup

✅ Seamless Customer Experience: Users don't notice deployment activity.

✅ Zero Downtime

Both environments run simultaneously.
No service interruption.


Example :

suppose :

Blue  = myapp:v1
Green = myapp:v2

Users use v1.--->Deploy v2 to Green.---->Test Green.---->Switch Service/Load Balancer to Green.

If issue occurs:

Green ❌
Switch back to Blue ✅

==============
apiVersion: apps/v1
kind: Deployment

metadata:
  name: k8s-boot-demo-deployment-blue

spec:
  replicas: 3

  strategy:
    type: RollingUpdate

  selector:
    matchLabels:
      app: k8s-boot-demo
      version: v1
      color: blue

  template:
    metadata:
      labels:

        color: blue

========
Scenerio-Real time
===============
Your e-commerce application gets huge traffic during a sale.

Initially:

2 Pods
      ↓
CPU Usage = 30%

======
Suddenly thousands of users come.

2 Pods
      ↓
CPU Usage = 85%


=========
HPA detects high CPU and automatically creates more pods.

2 Pods → 4 Pods → 6 Pods


========
When traffic drops:

6 Pods → 3 Pods → 2 Pods


This saves cost and prevents application crashes.

Step 1: Deployment


apiVersion: apps/v1
kind: Deployment
metadata:
  name: springboot-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: springboot-app
  template:
    metadata:
      labels:
        app: springboot-app
    spec:
      containers:
      - name: springboot-app
        image: myrepo/springboot-app:v1
        ports:
        - containerPort: 8080

        resources:
          requests:
            cpu: "200m"
            memory: "256Mi"

          limits:
            cpu: "500m"
            memory: "512Mi"

Step 2: Create HPA

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: springboot-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: springboot-app

  minReplicas: 2
  maxReplicas: 10

  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
